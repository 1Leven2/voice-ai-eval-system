本报告按作业模板完成第一至第六部分；第七部分“提交材料”暂不填写。

一、系统整体方案

系统架构与流程

JSON/CSV/TXT/WAV/MP3 → 解析校验 → 场景/任务标注 → SQLite
                                           ↓
             指标引擎 → 规则诊断 → 可选 LLM → 证据结构校验
                                           ↓
                  样例详情 → 人工修订/审计 → JSON/CSV/HTML 报告

FastAPI 负责 API 和页面，Jinja2 + 原生 HTML/CSS/JavaScript 负责界面，SQLite 保存样例、评测、修订和审计事件。app/metrics.py、app/diagnostics.py 和 app/audio_dataset.py 分别负责指标、诊断和真实音频索引。

技术选型与可靠性

使用 Python 3.10、FastAPI、Uvicorn、Jinja2、SQLite、pytest、httpx、Python 标准库 json/csv/wave。导入错误逐条返回，重复 ID 和不支持格式不会阻断整批；结果保存到 data/eval.db 和 data/exports/。普通用户可双击 start.bat 或运行 start.sh，自动准备数据、启动服务并打开浏览器。

三、指标、字段与 Prompt 设计

指标方法与阈值
CER/WERLevenshtein 距离除以参考长度；大于 0.2 诊断为识别差异较大
关键词召回命中关键词数/参考关键词数；小于 1 诊断漏识别
意图/槽位意图相等为 1；槽位匹配数/参考槽位数
术语一致性输出出现的术语数/要求术语数
延迟读取原始日志字段，没有字段为 -
座舱安全区分请求侧与输出侧命中：仅当系统输出偏离请求转写且仍含禁止操作时判违规、结论失败；输出仅为请求原文转写时标记 safety_assessable=false，结论需关注

核心 Prompt

仅基于 evidence 判断问题，不得补造事实。
返回 JSON：diagnosis、impact、suggestions、final_conclusion。
如果证据不足，保留“证据不足”，不要猜测音频内容、语种、说话人或模型输出。

LLM 只在三个环境变量同时存在时调用；网络错误、结构错误和非法结论自动回退规则诊断。最终 evidence 始终来自原始记录或规则指标，缺失字段使用 -。

结构化记录字段包含：样例 ID、场景类型、任务类型、输入数据/音频信息、参考标注/系统输出、量化指标、质量诊断/证据片段、影响评估/优化建议、人工修订/最终结论。

四、使用 AI 完成研发的过程

  1. 需求拆解：使用 Codex 将 PDF 要求拆为数据模型、指标引擎、诊断适配器、API、页面、测试和文档，并人工确认 100 条总量与 10 条报告展示量的区别。
  2. 测试先行：先写 CER/WER、关键词、槽位、CSV 导入和 API 测试，再实现最小代码；人工验证了 CSV 分隔符、重复 ID 和批量错误行为。
  3. 调试与真实音频：根据完整堆栈定位 Starlette 模板兼容问题；随后为 43 个 WAV 建立文件名标签索引，确认 system_output 必须保持 -，并增加 --reset 与一键启动器。

本次未事先记录精确工时，因此不虚构节省小时数；可验证结果是 36 项自动化测试、143 条可重复运行记录、完整设计/计划/审查/报告文档。

六、不足与 AI 提效总结

  1. 真实 WAV 目前完成索引、元数据展示和试听，尚未接入 ASR/音频分类模型，模型输出为 -。
  2. 场景/任务自动标注是透明启发式规则，不等同于训练好的分类模型。
  3. 系统没有认证、多租户和生产级上传安全；MP3 无额外解码器时未知字段为 -。
  4. AI 解决了需求拆解、测试生成、指标实现、导入兼容、页面调试、音频索引和文档整理；人工仍需把关标注、阈值、安全结论、证据和最终报告。
