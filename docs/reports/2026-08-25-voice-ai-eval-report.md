# 多场景语音智能体验评测与问题分析系统研发 AI 提效实践报告

## 一、系统总体方案

系统使用 FastAPI 提供 API 和页面，SQLite 保存样例、评测和修订，Jinja2 提供轻量页面。内置合成数据用于稳定演示，同时支持外部结构化文件和音频文件导入。核心链路为：

`导入 → 校验 → 场景/任务标注 → 指标计算 → AI/规则诊断 → 人工修订 → JSON/CSV/HTML 导出`

项目代码位于 `app/`，样例和导出位于 `data/`，测试位于 `tests/`，研发文档位于 `docs/`。

## 二、测试场景与样例设计

内置 100 条合成结构化样例；另从 `data/audios/` 索引 43 条真实 WAV：

| 场景 | 数量 | 子场景/链路 |
| --- | ---: | --- |
| 语音交互 | 40 | 单轮指令、多轮上下文、ASR/NLU |
| 语音翻译 | 30 | 中英互译、术语一致性、机器翻译 |
| 车载座舱 | 30 | 媒体/导航指令、安全规则、语义理解 |

每条样例拥有唯一 `sample_id`，并保留输入、参考、系统输出、音频元数据、指标、诊断证据和结论。

真实音频索引记录使用文件名（去掉扩展名）作为 `reference.label`，并保存原始相对路径。由于当前没有音频分类模型，`system_output` 保持 `-`，避免把参考标签冒充模型结果。

## 三、指标、Prompt 与结构化输出

系统计算 CER/WER、关键词召回、意图准确率、槽位匹配率、术语一致性、响应延迟/首包时间和座舱安全规则命中。

默认规则诊断可离线运行；可选 LLM 指令要求“仅基于 evidence 判断问题，不得补造事实”。若证据不存在，系统输出“证据不足”。

## 四、AI 辅助研发过程

1. 需求拆解：将需求拆成数据模型、指标引擎、诊断适配器、API、页面、导出和文档审查任务。
2. 代码生成与测试：先编写指标、导入和 API 测试，再实现最小代码；测试过程中发现并修正 CSV `task_types` 解析和新版 Starlette 模板调用差异。
3. 调试与重构：发现同步 FastAPI 端点在当前 AnyIO 环境的测试客户端会挂起后，改为 async 端点并用 ASGITransport 验证；页面渲染测试进一步捕获详情页 JSON 模板参数问题。

AI 参与了需求拆解、模块草拟、测试用例设计、错误定位和报告整理；最终行为由自动化测试、编译检查和 100 条样例演示验证。

## 五、系统运行与测试结果

执行：

```bash
python3 scripts/generate_samples.py
python3 scripts/run_demo.py
pytest -q
python3 -m compileall -q app scripts
```

结果：

- 导入：100 条合成样例 + 43 条真实音频，拒绝 0 条
- 评测：143 条，处理失败 0 条
- 场景分布：交互 40、翻译 30、座舱 30
- 结论分布：通过 80、需关注 5、失败 15
- 自动化测试：20 passed
- 输出文件：`data/exports/evaluation.json`、`evaluation.csv`、`evaluation.html`

典型座舱失败样例会记录“回复触发车载安全边界”，并在证据中保留命中的禁止操作文本。

## 六、不足与 AI 提效总结

当前不足：合成样例仍用于量化指标演示；真实 WAV 已接入索引和元数据展示，但尚未接入 ASR/音频分类模型，MP3 时长在无外部解码器时保持 `-`；没有认证和多租户能力；LLM 返回值的生产级 schema 校验和脱敏仍需增强。

AI 提效主要体现在：将需求快速拆成可测试模块、生成 100 条可追溯样例、补齐指标和诊断边界、定位模板兼容性问题，并同步产出设计、计划和审查记录。人工仍需把关指标阈值、诊断证据、车载安全结论和最终报告内容。
